# 云湃电商 Agent 0.21.0 技术实现说明

日期：2026-07-22  
候选版本：`0.21.0`  
数据库：schema v21

## 1. 当前实现结论

系统采用“模块化单体 + 多个持久 worker”的单机一体机路线，而不是把所有功能塞进一个大模型。FastAPI 提供身份和接口边界，LangGraph 只负责有界规划，业务服务负责确定性规则，SQLite 保存事实、状态机、版本和审计，管理后台只调用同源 API。

0.21.0 重点把人工接管从“可手工智能分配”推进为“可排班、可心跳、可自动恢复的持续派单”。新任务与派单作业同事务写入；worker 使用数据库租约竞争执行；坐席只有同时满足凭据、档案、实时心跳、班次、队列技能和容量条件时才会自动入选；无可用坐席形成持久告警，恢复值守后等待作业被唤醒并自动闭环。

本版本是本地代码级候选。真实淘宝权限、真实客户排班、真实模型和客户标注集、目标设备长稳与容量尚未验收，因此不能据此开启生产无人值守自动回复。

## 2. 总体技术路径

```text
合法渠道 / ERP/OMS / 虚拟连接器 / 管理后台
  -> FastAPI：认证、租户绑定、限流、正文限制
  -> 会话身份绑定、输入脱敏、可信上下文装配
  -> LangGraph：预检 -> 检索 -> 规划 -> 决策门
       -> 回答 / 追问 / 观察 / 动作 / 转人工 / 拒绝
  -> ToolRegistry + SOP Runtime：权限、参数、幂等、后置验证
  -> 输出安全门和高风险最终保护
  -> 事实、消息、快照、任务、事件、审计同源持久化
  -> 渠道 Agent / outbox / 竞品 / SLA / 自动派单 worker
```

核心原则：模型负责理解和建议，代码负责身份、权限、状态迁移、成功判定和风险放行。模型不能把顾客正文变成可信授权，也不能自行决定退款成功、竞品同款成立或坐席具备接单资格。

## 3. 运行和数据底座

### 3.1 API 与身份

- `api.py` 组装聊天、经营、人工接管、渠道和管理路由。
- `auth.py` 用派生哈希保存客户端和管理员密钥；请求 actor 只来自已认证身份。
- 外部会话 ID 与租户、客户端及主体 HMAC 绑定，跨身份复用会被拒绝。
- 客户端是否可提供订单上下文由服务端凭据能力决定，正文中的 `authorized` 无效。
- `/health` 暴露 schema、队列和 worker 状态；`/ready` 对必要 worker、磁盘和发布门禁执行硬检查。

### 3.2 SQLite 与事务

- 业务库和 LangGraph checkpoint 分库存储；业务库使用 WAL、busy timeout、外键和顺序迁移。
- 共享写路径使用进程内写锁和显式事务；任务、策略和运营配置再使用 `record_version` 乐观锁。
- schema v21 新增班次、派单作业和派单告警；启动后校验表、列、索引、外键和触发器，伪造迁移版本不能绕过物理检查。
- 数据目录有跨进程运行锁，单机阶段不允许两个服务实例共同写同一目录。

### 3.3 Worker 模式

每个异步域都使用同一类可靠性模式：业务意图先持久化，worker 原子领取，租约过期可恢复，失败按明确语义重试或转人工，结果写回同一账本。当前包括渠道 Agent、可靠发送、竞品监控、SLA 和自动派单 worker。

## 4. 智能客服模块

### 4.1 会话与可信上下文

实现：`service.py`、`context_builder.py`、`policy.py`、`database.py`。

1. 认证并绑定租户、客户端、主体和会话。
2. 在进入 LangGraph checkpoint 前对白名单上下文做清洗和脱敏。
3. `ContextBuilder` 固化身份、商品、订单、物流、SOP、知识、工具结果和冲突检查。
4. decision/generation 两阶段快照保存父子关系、authority、freshness 和 SHA-256。
5. 消息、人工任务和审计引用同一快照，后台可以回看回答依据。

身份或授权冲突在调用模型前就会澄清或转人工，不让模型补齐权限。

### 4.2 LangGraph Agent

实现：`graph.py`、`decision.py`、`llm.py`、`rag.py`、`prompts.py`。

- 图流程为 `intake -> precheck -> retrieve -> deliberate -> decision_gate`。
- 结构化决策只接受 `answer/clarify/observe/act/handoff/refuse/finish`。
- `observe/act` 形成最多 4 步的有界 ReAct；工具 Observation 回到模型继续规划。
- Pydantic 先验证模型输出，代码再验证步骤预算、工具权限、SOP、风险和后置条件。
- 最终回答再次执行来源、敏感信息和高风险动作检查；旁路会被转换为人工任务。
- `MODEL_ENABLED=false` 时不调用外部模型；需要规划的请求安全转人工。

### 4.3 人工接管队列

实现：`handoff.py`、`handoff_staffing.py`、`handoff_dispatch.py`。

- 默认队列覆盖投诉高风险、售后、技术异常和通用兜底。
- 路由按显式队列、reason、intent、risk 和 catch-all 确定，重大风险提升优先级。
- 任务状态为 `proposed -> accepted -> working -> input_required/review -> completed`，另有失败、拒绝和取消终态。
- 创建时固化首响/解决 SLA；任务的领取、转派、升级、备注和迁移都写不可变事件。
- 负责人操作受 owner 门和任务版本约束；并发更新只能有一个成功者。

### 4.4 坐席档案、心跳与排班

schema v21 将四类状态分开：

| 对象 | 用途 |
|---|---|
| 管理员凭据 | 是否允许登录和操作 |
| 坐席档案 | 启停、技能、容量、派单模式、排班模式 |
| presence session | 本次值守会话、连续 heartbeat sequence、短租约 |
| shift | UTC 绝对起止时间、有效/取消状态和版本 |

- `dispatch_mode=automatic/manual` 分离自动候选和仅人工分配坐席。
- `schedule_mode=unrestricted/scheduled` 决定是否要求当前时间落在有效班次内。
- 心跳必须由坐席本人发起；序号必须连续。相同序号和相同载荷可幂等回放，跳号、旧号或不同载荷重放会被拒绝。
- 档案 `record_version` 和在线 `presence_version` 分离，心跳不会制造档案编辑冲突。
- 保存本人档案会终止旧值守会话，前端同步停止定时器，防止旧心跳覆盖新配置。
- 班次使用带时区时间进入 API，服务端统一保存 UTC；重叠班次被拒绝，取消采用乐观锁并写脱敏审计。
- 当前只实现绝对时间班次，尚未实现周期规则、节假日模板、换班审批和工时统计。

有效自动候选必须同时满足：

```text
credential_status == active
and profile_status == active
and dispatch_mode == automatic
and effective_presence == available
and (schedule_mode == unrestricted or current_time in active_shift)
and member_of_target_queue
and global_active_tasks < operator_limit
and queue_active_tasks < queue_limit
```

### 4.5 持久自动派单

新任务创建和 `handoff_dispatch_jobs` 入队在同一事务完成。启动时 `ensure_pending_jobs()` 为历史 `proposed` 任务补齐缺失作业，防止升级或异常退出留下孤儿任务。

作业状态：

```text
pending -> leased -> assigned
                   -> waiting -> leased
                   -> failed -> pending（管理员带版本重试）
                   -> cancelled
```

- 领取使用单条条件更新和 `lease_owner/lease_expires_at`；并发 worker 只有一个能持有作业。
- 租约过期的 `leased` 作业可再次领取，支持进程强杀后的恢复。
- 自动分配排序为全局负载率、主队列、技能等级、活动任务数、稳定坐席 ID。
- 自动 worker 只消费 `dispatch_mode=automatic`；手工 `claim/reassign` 仍可使用符合人工资格的坐席。
- 无候选时作业进入 `waiting`，按指数退避再次尝试，并为同一任务创建或更新持久告警。
- 坐席上线、心跳或进入班次时会唤醒其租户内可处理的等待作业，降低恢复延迟。
- 技术错误达到最大次数进入 `failed`；无坐席是资源等待，不因尝试次数被错误丢弃。
- 任务已被其他路径分配时，worker 对账为 `assigned`；任务不再可分配时作业转 `cancelled`。
- 分配成功或任务取消会自动解决相关告警。

告警保存 `reason`、发生次数、首次/最近时间、脱敏详情和版本。管理员可在后台填写说明确认；worker 的新一次发生可能提升版本，此时旧弹窗提交返回 409，页面保留错误供刷新后重新判断。

## 5. 竞品分析模块

实现：`business/competitive.py`、`operations_api.py`、竞品 worker。

### 5.1 可信数据入口

- 竞品观察只能经 Connector 或管理 API 进入，必须带来源、来源引用、观察时间、估算标记和载荷哈希。
- 旧版本拒绝；同版本同载荷幂等；同版本不同载荷冲突。
- 当前虚拟淘宝连接器只生成本地样本，显式返回 `virtual=true`，不访问真实淘宝。

### 5.2 同款匹配

- 以 GTIN、品牌、型号、标题和关键属性计算确定性解释分、缺失字段和硬冲突。
- 自动结果只形成 `pending` 候选，管理员按版本批准或拒绝。
- 只有 `approved` 关系的价格、卖点和脱敏聚合口碑能进入 Agent 分析。
- 撤销匹配会让相关证据退出，并重评/解决不再成立的告警。

### 5.3 监控与告警

- 每店铺/SKU 保存低价幅度、竞品降价、新鲜度、估算数据和 approved-only 策略。
- worker 与手工“立即评估”调用同一原子服务。
- 告警支持 open/acknowledged/resolved、证据幂等、条件清除和新证据复发。
- 该模块输出证据、风险和建议，不自动改价。

## 6. 商品、库存、订单和指标

- 商品：保存 SPU/SKU、渠道状态、价格、属性、来源时间、哈希和版本。
- 库存：计算可售量、覆盖天数、缺货/滞销风险和补货建议，不执行采购或调拨。
- 订单：在事务内保存订单行、脱敏买家、物流、售后和不可变历史，不自动退款或赔付。
- 指标：只接受类型化 `QuerySpec`，不接受 SQL；返回指标定义版本、水位、质量和证据量。
- `OperationsService` 将已实现的只读能力注册为 Agent 工具；业务模块不直接访问第三方 HTTP。

营销和财务仍处于规划状态，模块注册表不会把它们报告成已完成。

## 7. 知识、SOP、自进化和质检

- 知识按平台、行业、店铺、商品和进化五层隔离；Agent 只检索当前租户和范围内已批准版本。
- SOP 使用类型化 DSL，版本链为 `draft -> evaluated -> approved -> active -> retired`；在途会话固定版本。
- SOP 步骤逐项持久化。读失败可在预算内恢复；写入或补偿未知态必须人工读回，不自动重放。
- 自进化只把人工纠正形成候选知识，经安全、检索碰撞、回归和管理员批准后生效；不能改权限、代码、Prompt、风险规则或模型权重。
- 质检规则检查证据、fallback、漏转人工、敏感信息和渠道发送风险；结果进入 VOC 和人工复核，不直接改线上规则。

## 8. 客户评测、发布和熔断

- 脱敏评测集按 suite/case 不可变版本保存并计算逐级哈希。
- 运行时通过 SQLite 快照创建隔离 Agent，执行真实多轮流程，主库不产生会话、消息和人工任务污染。
- 指标覆盖通过率、意图、转人工混淆矩阵、证据、fallback、严重失败、场景和跨版本回归。
- 发布策略提供 shadow/assist/collaborative/automatic；自动和人机协同要求第二管理员审批。
- 会话使用稳定哈希分流；运行错误超过预算时自动暂停。

## 9. 渠道接待与可靠发送

- 淘宝路线只使用店铺 OAuth、奇门机器人消息和 TOP 异步回写，不使用千牛页面自动化、Cookie 或协议逆向。
- 入站事件与渠道 Agent job 同事务落库；worker 用租约、幂等 invocation、退避和死信恢复。
- shadow 模式禁止草稿、人工任务、SOP 和 outbox 副作用。
- 回复先进入 AES-GCM 加密 outbox。调用前可证明未送出的错误允许重试；调用后的未知结果转 `uncertain`，必须人工核对。
- 会话所有权在发送前再次检查，人工接管后已排队自动回复会被拦截。

## 10. 管理后台

`/admin` 是无构建步骤的响应式页面，页面不直连数据库，也不复制服务端状态机。当前视图包括经营总览、智能客服、商品库存、订单售后、竞品分析、知识/SOP、质检/VOC、客服评测、渠道接待、发布门禁、模块和审计。

0.21.0 新增：

- 自动派单作业状态、worker 状态、立即调度和失败重试；
- 持久派单告警、确认处置和自动解决回显；
- 坐席自动/人工派单模式、排班模式、绝对时间班次新增/取消；
- “开始/停止值守”心跳，会话每 45 秒续租 120 秒；
- 正式的派单处置弹窗，替代不兼容且不可表达并发错误的原生 `prompt()`。

宽表在自身容器内横向滚动，页面主体不产生横向溢出；桌面和 390 x 844 视口均完成真实浏览器检查。

## 11. 运维与失败恢复

- 自动派单默认启用，配置项见 `HANDOFF_DISPATCH_*`。
- `/health` 的 `handoff_dispatch.worker` 提供运行、周期、累计分配/等待/失败、最近时间和错误。
- `/ready` 的 `handoff_dispatch_worker` 在启用时必须为 true。
- 管理员可执行单轮调度、查看等待/失败作业、带版本重试、确认告警。
- 无坐席时应先核对凭据、档案、心跳、班次、队列和容量，再恢复值守；不应直接修改任务负责人或数据库。
- 详细处置步骤见 `docs/handoff-dispatch-runbook.md`。

## 12. 当前边界

可以作为本地演示、隔离客户 PoC 和下一轮客户数据接入的候选，但以下事项仍是生产 Gate：

- 真实淘宝/ERP 权限、测试店铺和消息收发联调；
- 真实客户脱敏多轮标注集和固定模型/知识/SOP/事实基线；
- 客服主管签收组织、周期排班、节假日、技能、容量、SLA 和升级责任；
- 目标一体机 24/72 小时长稳、峰值容量、断网、限流、时钟漂移、强杀和磁盘故障；
- 设备密钥、异机恢复、安全测试、业务验收和最终审批。

完整验证证据见 `docs/TEST_REPORT_0.21.0.md`。
