# 架构与边界

## 目标

本服务是云湃电商一体机的轻量经营 Agent 与业务控制面。商品、订单、仓储、竞品、营销、财务、指标和客服是独立业务模块；LLM 负责理解用户目标、选择通用执行语义、选择已注册工具并根据执行结果继续规划，固化代码负责身份、事实、权限、业务规则、指标、幂等、后置验证、审计和人工接管。

平台适配器负责合法授权、验签、消息去重和平台回写。模型不接触平台密钥，也不能通过正文获得或提升权限。

## 业务模块

- `business/registry.py` 是业务模块目录，记录每个模块的职责、边界、实现状态和 Agent 工具。
- `business/inventory.py` 已实现库存余额、库存覆盖天数、缺货/滞销识别与补货建议；它不替代 WMS，也不执行采购和调拨。
- `business/competitive.py` 已实现可解释同款候选、人工裁决、价格/卖点/脱敏聚合口碑、持久告警与 approved-only Agent 门禁；每条记录必须带来源、时间和估算标识，不允许抓取或伪造未授权数据。
- `business/catalog.py` 已实现商品/SKU 事实、来源哈希、版本冲突和旧数据防覆盖。
- `business/orders.py` 已实现订单行、脱敏物流、售后单、原子聚合更新和不可变版本历史。
- `business/metrics.py` 已实现六项代码化指标；查询只接受类型化 QuerySpec，不接受 SQL。
- 营销和财务仍为规划状态，API 不会把它们报告成已完成。

业务域不得直接访问第三方 HTTP。所有外部事实和动作都必须通过 `connectors/base.py` 定义的统一 Connector 契约。

## 虚拟淘宝连接器

`connectors/virtual_taobao.py` 是当前可运行接口，提供连接测试、商品/订单/库存/竞品样本拉取、Webhook 签名验证、动作幂等和回执验证。其能力声明始终包含 `virtual=true`，不会访问淘宝或被 readiness 误报成真实授权。

真实淘宝代码保留为后续适配草案，但在取得官方权限、测试店铺和消息路由前不是当前功能依赖。

## LangGraph 主链

```text
START
  -> intake
  -> precheck
       refuse：提示注入、越权数据请求
       handoff：缺少可信订单身份上下文
       retrieve：正常业务请求
  -> retrieve（无预设业务意图的初始 RAG）
  -> deliberate（LLM 输出 AgentDecision）
  -> decision_gate（结构、循环预算、SOP 版本和完成条件）
       answer  -> 按 LLM 意图精排 RAG -> generate -> output verify
       clarify -> 向用户询问缺失参数
       observe -> tool_gate -> execute_tool -> verify_tool -> deliberate
       act     -> SOP 守卫/允许工具 -> tool_gate -> execute_tool -> verify_tool -> deliberate
       finish  -> 基于已验证工具结果生成回复
       handoff -> 持久人工任务
       refuse  -> 明确拒绝
  -> persist
  -> END
```

`observe/act -> tool result -> deliberate` 构成有界 ReAct 循环，默认最多 4 步。具体退款、取消、改价、补发等业务不拥有独立硬编码图节点，而是由动态工具目录提供。

## 决策权与放行权

LLM 可以决定：

- 用户目标、意图、实体和缺失参数。
- 使用知识回答、追问、查询外部状态、执行操作、结束或转人工。
- 从当前工具目录中选择工具、组织参数和安排调用顺序。
- 根据最新 Observation 继续、改道或结束。

代码必须决定：

- 工具是否注册、读写类型是否匹配、参数是否通过 Pydantic schema。
- 可信上下文、权限、人工注入业务规则和风险阈值是否允许。
- 写工具是否提供幂等字段和后置验证器。
- 外部结果是否达到后置条件，是否可以声称完成。
- 循环预算、异常、重试和人工接管。
- 当前意图是否存在活动 SOP、必需上下文是否齐全、外部写是否允许、工具是否列在 SOP 的 `act` 步骤中。

路由和工具说明会动态注入决策 Prompt，但 Prompt 不是安全边界。`decision_gate` 和 `ToolRegistry` 拥有最终放行权。

## 工具契约

`ToolSpec` 至少包含：名称、说明、读写分类、输入模型、处理器、可信上下文字段、超时和重试元数据。写工具还必须包含幂等字段和后置验证器，否则无法注册。

模型只输出 `tool_name + arguments + expected_outcome`。工具门再次验证全部参数和策略后执行。工具结果以 Observation 回到模型；`postcondition_met=true` 之前，`finish` 和完成性回复都不会通过。

当前动态目录已注册商品、订单、库存、竞品价格、竞品综合证据和经营指标六个只读工具。订单查询必须同时匹配可信订单号和店铺号；工具调用业务模块而不是直接查外部系统。执行器落实超时、只读重试、写超时不确定态和后置验证；未注册能力仍会产生持久人工任务，不会伪装执行。

## 分层知识与 SOP

SQLite 保存知识正文、租户、层级、店铺/SKU 范围、来源、不可变内容版本、生命周期版本、状态、校验和与审批人。内置知识为全局只读基线，租户知识只在相同租户和匹配店铺/SKU 范围内可见。中文检索使用字符 n-gram 哈希向量和词项重合度混排，不依赖独立向量服务。

RAG 提供商品、店铺、流程、工具说明与话术证据，不承载权限、金额阈值或风险规则。完全匹配且经人工批准的进化答案可以绕过模型直接复用，但仍经过输出安全门。

SOP 使用类型化 JSON DSL，步骤具有稳定 ID、操作、能力、尝试上限、人工审批和可选补偿工具。内容版本不可原地修改；发布链为 `draft -> evaluated -> approved -> active -> retired`，评测会校验高风险动作审批、读写工具类型和补偿工具是否已注册，激活新版本会原子退役旧活动版本。首次执行时写入 `sop_runs` 和逐步骤 `sop_step_runs`，同一会话固定启动版本。步骤按顺序推进，可信上下文缺失会等待输入，评估/提案及声明审批的动作会等待管理员，所有步骤完成后 run 才能完成。读取中断可在尝试预算内恢复；写入或补偿中断进入 `uncertain`，禁止自动重试，必须带乐观锁进行人工读回核对。已成功动作可调用 DSL 声明的注册写工具执行补偿，补偿结果和哈希单独留痕。

## 质检与客服操作

`qa_results` 保存代码化问题、证据 ID、规则集版本、得分和人工复核状态，不保存额外原始顾客信息。质检结果只进入 VOC 汇总和候选改进，不直接改变知识、SOP 或风控。

渠道会话所有权为 `bot/human/paused`，迁移使用会话版本乐观锁。人工回复先写入 `channel_reply_drafts`，同时保留脱敏 AI 建议、人工终稿、结构化 diff、证据、SOP 引用、风险和草稿版本。发送先持久化 AES-GCM 加密载荷和 outbound 事件，再由带租约 worker 逐条派发；派发前再次检查当前所有权。连接建立失败可按退避重试，外呼后中断只能标记 `uncertain` 并等待带版本的人工核对，禁止盲目重发。

## 人工接管队列与 SLA

人工接管不是一条无负责人记录。`handoff_queues` 按租户保存原因/意图/风险路由、默认优先级、首响/解决 SLA、单坐席容量和升级队列；系统提供投诉、售后、技术异常和通用兜底四个默认队列。高风险请求至少提升为高优先级，重大风险为紧急。最后一个兜底队列不能停用，非法规则、自升级或跨租户队列 fail closed。

任务按 `proposed -> accepted -> working -> input_required/review -> completed` 的受控状态机推进，终态必须有处置说明。认领、转派、备注、升级和迁移都使用任务版本乐观锁；认领还原子检查未分配状态和坐席容量。`handoff_task_events` 以任务版本保存不可变前后状态、队列、负责人、操作者和脱敏说明。

任务创建时固化首响和解决截止时间，开放任务动态计算正常、即将到期和违约。SLA worker 默认每 30 秒扫描全部租户：首响违约升级到 L1，解决违约升级到 L2；已有级别重复扫描跳过，并发版本冲突不覆盖坐席操作。

schema v21 在凭据、坐席档案、队列技能和容量基础上增加自动/人工派单模式、绝对时间班次、显式 presence session 与连续 heartbeat sequence。任务和派单 job 同事务创建，自动派单 worker 通过数据库租约单赢家领取；只有自动模式、心跳在线、班次内并满足队列/容量资格的坐席进入候选。无候选时 job 等待并形成持久告警，恢复值守会唤醒作业，成功分配或任务取消自动解决告警。领取、转派和自动分配共用资格门，自动路径额外要求 automatic 和 on-shift。health/ready 暴露并校验 worker 状态。完整契约见 `docs/TECHNICAL_IMPLEMENTATION_0.21.0.md`。

## 回放、灰度与运行熔断

`release_policies` 保存不可变的策略版本和可变生命周期状态。策略范围固定为租户、平台和店铺，包含运行模式、流量百分比、意图白名单、最高风险、证据/模型降级要求、回放阈值和运行错误预算。状态链为 `draft -> evaluated -> approved -> active -> paused/retired`；启用同范围新版本时，旧活动版本在同一数据库事务中退役。

回放不是静态样例比较。服务先使用 SQLite online backup 复制当前业务库和 checkpoint 库，在临时运行目录创建隔离 Agent，再使用临时租户客户端执行完整 LangGraph。源运行目录的会话、消息、任务和 checkpoint 不被污染。持久报告只包含用例 ID、断言结果、错误类别、统计和数据集 SHA-256，不保存原始问题或答案。

奇门入站先使用发布盐、租户、平台、店铺和会话 ID 计算稳定 SHA-256 桶。未选中流量时不调用 Agent；`shadow` 只记录输出，`assist` 写入人工草稿，`collaborative/automatic` 只有在意图、风险、证据和模型降级规则全部通过后才能发送。回答违规、发送拒绝、不确定态、死信或发送异常会写入幂等运行观测；超过严重错误或失败率预算时策略自动暂停。自动和人机协同策略要求第二个管理员审批，管理员操作和自动暂停全部审计。

## 版本化客户评测

`evaluation_suites/cases/runs/case_results` 保存租户隔离的脱敏标注集、不可变版本、数据集哈希、实际多轮 Agent 运行和结构化结果。草稿用例整体原子替换，冻结前检查最少用例与必需场景；运行前重新验证逐 case 和数据集 SHA-256，防止绕过服务层篡改。

评测在 SQLite 临时快照中创建关闭常驻 worker 的隔离 `AgentService`，同一 case 的多轮对话复用 session，主库不新增会话、消息、人工任务或 checkpoint。指标覆盖通过率、意图、转人工混淆矩阵、证据、fallback、场景、严重失败和跨版本回归。基线只比较相同 `suite_key` 且 `case_key + case_hash` 未变化的用例；结果可带乐观锁应用到发布策略，失败评测不能审批。

## 自进化

```text
人工负反馈 + 修正答案 + 证据来源
  -> pending candidate
  -> 静态安全 + 检索适配 + 碰撞检查 + 基线回归
  -> evaluated
  -> 管理员批准
  -> 租户知识 active
  -> 可回滚 retire
```

自进化只更新知识和已批准话术。权限、金额限制、风险规则、工具代码、系统 Prompt 和模型权重不允许自动修改。

## 虚拟店铺跨模块验收

0.22.0 内置显式 `virtual=true` 的“晴川生活电器旗舰店”关联数据包。模拟器先用 Pydantic 领域模型校验，再通过商品、库存、订单、竞品和知识公开服务写入 schema v21；不直接插表，因此来源版本、竞品同款审批、知识生命周期、租户隔离和工具权限均不能被绕过。

13 个场景从同一店铺事实验证商品、订单/物流/售后、库存风险、受控指标、approved-only 竞品分析与持久告警、知识客服、可信订单范围、人工接管/自动派单、后台聚合、租户隔离、Connector 幂等以及冻结标注集的实际 Agent 隔离评测。报告再与业务模块注册表交叉核对：全部 7 个 `available` 模块必须有通过场景；`marketing/finance` 仍按 `planned` 报告，不伪造验收。完整契约见 `docs/VIRTUAL_STORE_SIMULATION_0.22.0.md`。

## 数据与运行治理

- 外部 `session_id` 与租户、客户端和用户 HMAC 绑定，内部 ID 作为 LangGraph `thread_id`。
- context 在进入 checkpoint 前完成白名单清洗和脱敏，正文中的 `authorized` 无效。
- SQLite 业务库当前为 schema v21，除经营事实外还包含不可变客服上下文快照、竞品匹配/内容/监控证据、分层知识字段、SOP 定义/版本/run/逐步骤执行与补偿账本、质检结果、客服回复草稿、持久 outbox 租约/核对、渠道事件/Agent 任务、人工接管队列/任务事件/SLA、坐席档案/心跳租约/班次/队列成员、持久派单作业/告警、发布策略、版本化客户评测和运行观测；checkpoint 仍独立存储，适合单机或单写实例。
- 灾备模块使用 SQLite online backup，按 checkpoint 后业务库的顺序生成独立一致快照，并验证 checkpoint thread 必须属于业务会话；快照清单与双库整体采用 AES-256-GCM + HKDF-SHA256 流式认证加密。
- 服务持有数据目录运行锁；在线备份不阻塞服务，恢复、回滚和第二实例启动必须获得互斥锁。恢复先校验再替换，旧库保留在独立回滚目录，回滚时当前版本同样保留为 forward 目录。
- 消息默认保留 30 天，审计默认保留 365 天；未决人工任务和进化证据受保护。
- 审计记录 LLM 决策模式、工具名称、工具状态、后置条件、ReAct 步数和人工原因，不记录模型隐式思维过程。
- 单机部署不提前引入 Redis、消息队列或独立向量数据库。
