# 云湃电商 Agent 0.17.0 技术实现说明

## 1. 本版本解决的问题

0.14.0 已具备版本化竞品价格监控和持久告警，但它仍默认相信上游给出的“本店 SKU ↔ 竞品 SKU”关系。若规格、套装、容量或型号并非同款，价格差和后续建议都会失真。此前也没有可追溯的商品卖点、聚合口碑证据及人工裁决历史。

0.17.0 把竞品模块改造成可信证据链：先建立可解释同款候选，再由运营人员批准或拒绝；只有已批准匹配关联的价格、商品卖点和聚合口碑才能进入 Agent 建议。价格建议仍为只读，不执行调价。

## 2. 端到端路径

```text
授权 API / 许可数据商 / 人工文件 / 虚拟样本
  -> 规范化本店与竞品商品身份
  -> 确定性匹配评分 + 匹配字段 + 硬冲突 + 缺失字段
  -> pending 质量队列
  -> 人工基于证据和乐观锁批准或拒绝
  -> 不可变裁决历史
  -> 价格观察、商品卖点、聚合口碑绑定 match_id
  -> 监控策略只选择 approved 匹配
  -> 持久告警 / 只读分析 / Agent 工具
  -> 后台持续复核；撤销匹配会使相关证据退出建议并重评告警
```

## 3. schema v17

| 表或字段 | 职责 | 关键约束 |
|---|---|---|
| `competitive_entity_matches` | 同款候选、评分、解释、人工状态 | `(tenant_id, connector_id, source_id)` 唯一；状态 `pending/approved/rejected`；`record_version` 乐观锁 |
| `competitive_match_decisions` | 不可变人工裁决历史 | 保存前后状态、匹配版本、操作人、依据和时间 |
| `competitive_signals` | 商品卖点与聚合口碑证据 | 只允许 `product_claim/review_summary`；来源唯一；关联匹配；摘要脱敏 |
| `competitor_observations.entity_match_id` | 价格观察绑定同款候选 | 服务层强制租户、店铺、本店 SKU、竞品名称和 SKU 一致 |
| `competitive_monitors.require_approved_match` | 监控证据门 | 新策略默认 `true`；v16 历史策略迁移默认 `false`，避免静默改变既有行为 |

v16 到 v17 只增加表和列，不重分类历史观察，不自动批准旧数据，也不重放历史告警。数据库启动时验证物理表和关键列，`PRAGMA user_version` 与迁移账本统一为 17。

## 4. 可解释同款评分

评分是确定性规则，不是不可解释模型。输入包括标题、品牌、型号、类目、GTIN 和最多 32 个规格属性；文本先做 NFKC、大小写和标点归一化。

| 证据 | 分值或行为 |
|---|---:|
| GTIN 精确一致 | 50 |
| 品牌精确一致 | 15 |
| 型号精确一致 | 20 |
| 类目精确一致 | 10 |
| 标题相似度 ≥ 0.85 / ≥ 0.70 | 10 / 5 |
| 指定关键属性全部精确一致 | 合计 15，按属性平均分配 |
| GTIN、品牌、型号、类目或关键属性不一致 | 记录硬冲突，建议拒绝 |

总分封顶 100。无硬冲突、分数至少 70、指定关键属性无缺失时，系统建议 `approved`；存在硬冲突时建议 `rejected`；其余保持 `pending`。即使系统建议批准，初始状态也始终是 `pending`，不能自动越过人工裁决。完整品牌、型号、类目、标题和规格可在无 GTIN 时达到人工复核门槛；GTIN 格式只接受 8/12/13/14 位数字。

系统不允许批准带硬冲突或未达到建议批准条件的候选。业务需要覆盖规则时，应先修正身份事实或新增正式规则版本，而不是由操作员无依据强行覆盖。

## 5. 写入、幂等和并发

匹配候选和信号以租户、连接器、上游 `source_id` 作为幂等范围，并对规范载荷计算 SHA-256：

- 同一来源、同一载荷重复写入返回原记录并标记 `idempotent`；
- 同一来源、不同载荷拒绝为版本冲突；
- 人工裁决使用 `expected_record_version`，并在一个事务中更新候选和写入决定历史；
- 同一版本多人并发裁决只有一人成功；
- 上游重试不会把已批准或已拒绝状态重置为 pending。

价格观察绑定匹配后不可通过同一观察键改绑其他候选，避免历史证据被静默替换。

## 6. 商品卖点与聚合口碑

信号只允许两种结构：

- `product_claim`：本店或竞品的结构化方面和脱敏摘要，不允许评论计数；
- `review_summary`：方面、脱敏聚合摘要、至少 5 个样本、正向数和负向数，正负向合计不得超过样本量。

Pydantic 使用 `extra=forbid`，因此评论者 ID、原始评论数组、订单号等未定义字段不能进入接口。摘要写库前执行手机号、证件号、银行卡和口令脱敏。系统不保存评论者或原始评论，也不把多个可能重叠的数据源盲目合并为唯一人数；分析只选择每个匹配、角色、类型和方面的最新证据，并保留来源。

成对口碑按正向率比较：竞品相对本店高至少 5 个百分点为 `competitor_advantage`，低至少 5 个百分点为 `subject_advantage`，其余为 `roughly_equal`；缺任一侧时标记 `insufficient_pair`。

## 7. 价格监控和历史兼容

新建监控策略默认 `require_approved_match=true`。评估 SQL 只选择：

1. 当前租户、店铺和本店 SKU 范围内的观察；
2. 满足估算数据策略的观察；
3. 绑定且状态为 `approved` 的匹配。

没有合格观察时生成数据过期/质量告警，不把未验证价格当成低价或降价事实。批准匹配会立即重评范围；撤销匹配会自动解决已失效的价格告警，并产生无合格证据提示。

v16 历史策略保留 `require_approved_match=false`，在后台明确显示该开关；但 Agent 工具仍执行自己的 approved 门禁，不把历史未验证观察送入模型。

## 8. Agent 工具

模块提供：

- `get_competitor_price_analysis`：兼容原工具名，改为已批准同款下的价格分析；
- `get_competitive_intelligence`：返回已批准同款下的价格、商品卖点、聚合口碑和证据。

工具输出会移除未批准观察和其价格告警，保留 `quality_gate`：是否要求批准、合格竞品数、排除的未验证竞品数。管理 API 可查看全部数据用于治理，模型只看通过门禁的数据。两项工具均为 L0 只读能力，没有调价、改标题或抓取动作。

单次分析最多读取最新 5000 条价格历史，并返回 `history_truncated`，避免无界历史把 Agent 请求拖垮。观察查询用一次 LEFT JOIN 带回匹配状态，避免逐条 N+1 查询。

## 9. 管理 API 和后台

新增租户隔离管理员接口：

```http
POST /v1/competitive/matches
GET  /v1/competitive/matches
GET  /v1/competitive/matches/{match_id}
POST /v1/competitive/matches/{match_id}/transition
POST /v1/competitive/signals
GET  /v1/competitive/signals
GET  /v1/competitive/quality
```

竞品后台新增同款匹配质量队列、状态筛选、匹配解释、硬冲突/缺失字段、来源、版本和页面内批准/拒绝对话框；监控表单新增“仅已批准同款”；价格明细显示门禁状态；内容区显示脱敏摘要、样本计数、匹配状态和证据来源。每次候选、信号和人工裁决同时写中央审计日志。

## 10. 运行边界

0.17.0 是本地代码级候选，不是生产放行：

- 尚未接入客户已授权的真实竞品数据供应商，也未完成真实字段映射和来源许可审计；
- 匹配阈值只经过确定性用例，尚未用客户商品对标集测量误报、漏报和运营一致性；
- 聚合口碑没有真实数据供应商的去重、时间窗和代表性验收；
- 当前 Agent 只读，不自动调价、修改商品或投放；
- SQLite 适合单机一体机，多实例阶段需迁移支持行级锁的数据库；
- 仍需完成脱敏客户回放、24/72 小时长稳、目标硬件容量、安全、异机灾备和业务签收。

建议上线顺序：合法来源确认 -> 真实只读导入 -> 人工匹配抽检 -> shadow Agent -> 业务签收 -> assist。任何自动价格动作都应作为独立高风险版本重新设计和验收。
