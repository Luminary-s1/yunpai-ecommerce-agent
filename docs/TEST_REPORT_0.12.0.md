# 云湃电商一体机 Agent 0.12.0 测试报告

## 1. 验收结论

- 测试对象：`yunpai-ecommerce-agent 0.12.0`，SQLite schema v12。
- 本地发布门禁候选：**通过**。本版在 0.11.0 加密灾备和 0.10.0 可靠发送基础上，交付版本化发布策略、隔离真实 Agent 回放、双人审批、稳定哈希灰度、四级运行模式、运行观测、错误预算和自动暂停。
- 生产放行：**不通过（NO-GO）**。真实淘宝/ERP 联调、首个客户脱敏回放、24 小时长稳、断电和资源耗尽故障演练、异机恢复、设备密钥托管、完整 SOP 补偿和语义 VOC 尚未形成证据。
- 本报告只证明 Windows 本机、SQLite 单写部署和虚拟/模拟依赖下的候选质量，不把虚拟淘宝、mock 模型或本机性能表述为真实生产能力。

## 2. 当前技术实现路径

系统继续采用“单机模块化单体 + 强边界 + 可按负载拆分”的路径：

```text
官方渠道 / ERP / 授权文件
    -> Connector 能力声明、验签、去重、版本和标准事件
    -> 业务事实层（商品、订单、库存、竞品、指标）
    -> 身份、租户、会话、可信上下文、知识和 SOP 组装
    -> LangGraph 有界 ReAct（模型只提出结构化决策）
    -> 工具注册、参数、权限、风险、证据和后置条件代码门
    -> 发布门禁（影子 / 提示 / 协同 / 白名单自动）
    -> 持久加密 outbox、租约 worker、平台回执与人工核对
    -> 质检、VOC、运行观测、自动暂停和全链路审计

发布前：源数据库 online backup -> 临时隔离 Agent -> 数据集断言
运行中：稳定会话分桶 -> 策略约束 -> 发送结果 -> 错误预算熔断
灾备：双 SQLite 快照 -> AES-256-GCM -> verify/restore/rollback/rekey
```

核心边界没有交给 Prompt：模型负责理解、检索、生成候选回答和选择已注册工具；固化代码负责身份、租户、状态机、参数类型、权限、幂等、成功判定、灰度放行、暂停和恢复。

## 4. 发布门禁实现

### 4.1 策略与生命周期

策略固定 `tenant + platform + store` 范围，保存模式、流量、意图白名单、最高风险、证据要求、模型降级策略、回放门槛和运行错误预算。相同 `release_key` 只增加版本，不能改变范围；状态链为：

```text
draft -> evaluated -> approved -> active -> paused / retired
```

所有转换携带 `record_version` 乐观锁。启用同范围新版本时，旧活动策略在同一 SQLite 事务中退役。`collaborative` 和 `automatic` 的创建人不能审批自己的版本。

### 4.2 隔离回放

回放使用 SQLite backup 复制当前业务库和 checkpoint 库，在临时目录创建完整 `AgentService`，为目标租户插入一次性内部客户端，再执行真实 `service.chat -> LangGraph -> RAG/tool/policy -> response` 链。回放关闭 outbox worker、自动回复和自身发布门禁，结束后关闭连接并删除临时目录。

源库的 session、message、handoff 和 checkpoint 数量在测试前后保持不变。持久报告只保存 case ID、断言结果、错误类别、实际意图/风险/证据数量/降级标志、统计和数据集 SHA-256，不保存原始输入或回答。

### 4.3 灰度模式

| 模式 | 选中流量中的行为 | 允许直接发送 |
|---|---|---|
| `shadow` | 执行 Agent 并记录观测，不改变 owner、不发消息 | 否 |
| `assist` | 切换人工 owner，创建带证据的 AI 草稿 | 否 |
| `collaborative` | 通过策略时发送；要求第二管理员审批 | 条件通过后 |
| `automatic` | 只对白名单、低风险、有证据、无禁用降级的回复发送 | 条件通过后 |

会话使用发布随机盐和 `tenant/platform/store/conversation` 计算 SHA-256 桶，分配范围为 0..9999；同一会话稳定入组。没有活动策略或未选中时，在 `RELEASE_GATE_REQUIRED=true` 下不调用 Agent、不发送，只记录阻断审计。

### 4.4 运行熔断

每个入站 event 在同一发布下只产生一条观测。意图越界、风险超限、缺少证据、禁用的模型降级、漏转人工和渠道投递失败进入违规统计。严重错误超过预算，或达到最少样本后失败率超过阈值，策略原子转为 `paused` 并写 `release.auto_paused` 审计。渠道异常、`rejected`、`uncertain` 和 `dead_letter` 会把已通过的回答观测升级为严重投递失败。

## 10. 生产放行剩余 Gate

以下任一项未完成，都不得把 0.12.0 标记为生产可用：

1. 淘宝客服机器人资质、正式 App/奇门/TOP 凭证、测试店铺真实入站、人工接管、回写、回执、重放、限流和核对。
2. 真实 ERP/OMS 商品、订单、物流、售后字段、增量同步、日对账、失败补偿和权限审计。

4. 至少 24 小时 soak，以及进程强杀、断电、磁盘写满、数据库锁、积压、平台超时/限流和 checkpoint 一致性演练。

7. 在真实渠道按 shadow -> assist -> collaborative -> automatic 顺序运行，每次扩量使用新版本；任何严重错误必须停止放量。
8. 目标一体机的移动/桌面浏览器、可访问性、磁盘容量、权限、全盘加密、日志和告警接入。
