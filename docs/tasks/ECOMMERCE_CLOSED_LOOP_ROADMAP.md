# 电商经营闭环 M7-R～M10-R 总路线

> 文档性质：后续里程碑的稳定产品边界、依赖关系和协作规则。
> 项目负责人、里程碑收口人及任务书维护人：**闫睿涵**。
> 工时、日期、完成比例、派发记录和实时阻塞只在负责人工作台网页维护。

## 1. 产品方向

后续开发服从刘经理已经确认的方向：先让纯电商闭环在真实经营场景中跑起来，
再用测试和使用反馈持续打磨。当前店铺只能查看、不能操作，因此第一阶段交付
不是“自动经营”，而是一套基于平台只读导出和人工配置的可演示闭环：

1. 把订单、商品、库存、履约物流、流量、广告、退款和收入等事实接进同一套只读底座。
2. 先跑销售与售后两类客服主任务，其他客服任务保留为后续扩展。
3. 复用 M5-R 形成商品/SKU 的流量诊断和生命周期建议，不默认修改存量标题或主图。
4. 复用 M6-R 形成销量预测、补货建议、订购单草稿和经营决策。
5. 订购单必须人工确认；利润字段不全时只展示缺口或“净利润试算（演示参数）”，
   不得冒充财务净利润。

这一阶段只做纯电商，不纳入生产工单，不替代商家 ERP，不自动采购、付款、改价、
改标题、换主图或报名活动。

## 2. 为什么申请四个团队任务文档

建议申请 **M7-R、M8-R、M9-R、M10-R 四个团队任务文档**。本文件作为共享母路线，
不再单独申请一个里程碑。

| 里程碑 | 围绕的经营问题 | 交付结果 | 主要复用 |
|---|---|---|---|
| M7-R 只读数据与 Demo 事实底座 | 现在能拿到什么、字段是否可信、能否安全复跑 | 可追溯的经营事实、数据准备度和只读 Demo 数据集 | F-202、F-208、F-303～F-309 |
| M8-R 销售与售后客服闭环 | 客服能否基于真实订单/库存/物流帮助销售和处理售后 | 只读影子模式下的销售/售后建议回复与独立评测 | M4、F-104、F-124～F-126 |
| M9-R 商品流量与生命周期经营 | 链接和 SKU 如何获得曝光，商品下一步该做什么 | 流量诊断、受控实验建议和人工确认的生命周期建议 | M5-R、F-312～F-316 |
| M10-R 预测补货与经营决策 | 备多少货、何时订、是否赚钱 | 预测/补货、订购单草稿、利润准备度和经营决策台 | M6-R、F-317～F-321、F-309 |

M7-R 是共同前置。M7-R 的导入契约冻结后，M8-R 与 M9-R 可以并行；M10-R 可先接
M6-R 的预测与库存计划，最终联调再消费 M8-R 的售后事实和 M9-R 的流量事实。

```text
                         ┌─> M8-R 销售 / 售后客服 ─┐
M7-R 只读事实底座 ──────┼─> M9-R 流量 / 商品经营 ─┼─> M10-R 经营决策收口
                         └─> 现有 M6-R 预测能力 ───┘
```

## 3. 当前可用事实与缺口

### 已有条件

- 已有千牛只读子账号，可用于了解页面和人工核对，但不得在页面执行任何变更。
- 已取得订单、商品、库存、履约物流、经营指标、推广、退款、收入和客服话术等只读样本。
- M4、M5-R、M6-R 已有本机能力可以复用，不另起第二套客服、流量或预测算法。

### 当前无法提供

- 采购成本。
- 可作为真实样本的一张订购单。
- 可用于正式计算的运输周期。
- 退货后二次销售的整备成本。

这些缺口不再反复向杨总追问。系统必须支持以后人工补录或接口接入；Demo 需要这些
字段时使用显式“演示参数”，缺失值不得默认为零。

## 4. 数据来源四态

所有进入经营结论的字段都必须带来源类型、数据时间和来源引用。唯一允许的来源类型为：

| 来源类型 | 含义 | 可用于什么 |
|---|---|---|
| 真实数据 | 平台/系统导出后经字段白名单、脱敏和版本校验的数据 | 在数据质量门通过后参与真实经营事实计算 |
| 人工配置 | 由有权限人员填写并确认的经营参数 | 参与计算，但必须显示配置人、版本和生效范围 |
| 演示参数 | 为跑通 Demo 而设置的假设值 | 只能形成演示结论，界面必须显式标注 |
| 缺失 | 当前没有可靠来源 | 阻断依赖该字段的正式结论，不得按零处理 |

真实导出中的顾客姓名、手机号、地址、原始聊天等敏感字段不得进入 Git、模型上下文、
普通日志或 Eval fixture。千牛登录态、Cookie 和页面内容不是 Connector 凭证，也不是
真实集成验收证据。

## 5. 刘经理与杨总讨论内容的覆盖关系

| 已讨论能力 | 规划归属 | 当前边界 |
|---|---|---|
| 链接、标题、主图、SKU 的平台内曝光诊断 | M9-R | 默认保持存量链接；只有错误、关键词陈旧或曝光/点击证据不足时才提出人工审核建议 |
| 智能客服销售与售后 | M8-R | 第一优先；只生成建议回复或影子结果，不在千牛自动发送 |
| 加购追单、退款挽留、大促提醒等客服次要任务 | M8-R 后续扩展 | 等销售/售后主任务和真实渠道跑通后再立项，不塞入首轮验收 |
| 商品选品、定价、活动、补货、清仓生命周期 | M9-R + M10-R | 输出可解释建议和人工确认项，不自动改价、报名或采购 |
| 竞品销售与对标 | 复用 F-304，供 M9-R/M10-R 消费 | 只接受授权、人工或文件来源；缺失时标记可选信号不可用，不阻断基础预测 |
| 历史/当日销量、曝光、点击、转化、广告、库存趋势 | M7-R + M10-R | 先验证字段、粒度和时间范围；缺失指标不伪造趋势 |
| 销量预测与补货 | M10-R | 复用 M6-R；baseline、质量门和数据新鲜度保持不变 |
| 根据料号生成订购单 | M10-R | 只生成草稿，前期人工确认；供应商交期只收集、跟踪，不由系统核交期 |
| 净销量与二次销售费用 | M10-R | 有可靠件数/费用才计入正式口径；否则显示缺失或演示试算 |
| 财务最终净利润 | M10-R | 必须扣齐配置口径内的广告、退货、逆向物流、入库/整备、采购等费用；不完整则不出正式净利润 |
| 种草 | 后续候选 | 按刘经理要求放到下一阶段，本轮不开工作包 |
| 生产工单、生产环节、替代 ERP | 非目标 | 纯电商范围内不实施，只预留合规接口 |

## 6. 团队协作与独立验收

项目负责人闫睿涵负责范围裁定、跨里程碑接口、任务书维护和最终收口；具体开发按各
WORKBENCH 的工作包表执行。正式验收采用固定轮转：

| 开发负责人 | 默认独立验收人 |
|---|---|
| 闫睿涵 | 胡磊 |
| 胡磊 | 缪海南 |
| 缪海南 | 谢良璇 |
| 谢良璇 | 闫睿涵 |

规则：

- 开发者可以编写并运行单元测试和自测，但这些结果不算正式验收。
- 独立验收人必须在开发者交付后独立读任务书、检查差异并复跑门禁；本包开发者不得
  代签自己的验收。
- 每个工作包至少要有一项能证明门禁真实生效的反例或 mutation；恢复后再跑绿态。
- 如果独立验收人参与了该包代码修改，必须按上表换给下一位未参与开发的人。
- 闫睿涵依据独立验收证据做里程碑收口，不以项目负责人身份覆盖失败结论。

## 7. 统一里程碑门禁

每个里程碑只有满足以下条件才能进入候选：

1. 本里程碑的前置契约已经冻结，所有来源、版本和缺失状态可追溯。
2. 工作包的开发负责人和独立验收人不同，独立证据已形成。
3. Demo 的真实数据、人工配置、演示参数和缺失数据在 API、页面和报告中一致显示。
4. 只读边界有反证；删掉写屏障或把缺失改成零时，测试必须失败。
5. 新 schema、字段、枚举和注册项只有一个权威定义；如需迁移，实施前重新扫描所有
   refs，并在 `CONTRIBUTING.md` 的占号表取得当时真实可用版本号。
6. 只声明已经验证的代码级结果；Demo、真实平台、财务和生产结论不得互相冒充。

## 8. 暂缓与后续入口

以下内容保留产品方向，但不作为 M7-R～M10-R 第一轮完成条件：种草、多平台同时铺设、
主动营销自动触达、生产工单、供应商生产排程、替代商家 ERP、自动采购/付款、自动改
标题/主图/价格和自动报名活动。待只读 Demo 和真实场景验证后，再根据实际缺口单独立项。

## 9. 实现纪律

- 遵守 D-034：模型决定用户意图和语义下一步；代码只基于权限、数据完整性、schema、
  新鲜度、状态机、幂等和后置验证决定当前能否安全执行。
- 遵守 D-035：共享枚举、字段表、公式、阈值、版本和注册表只定义一次；测试断言本包
  增量与边界，不冻结全局数量或完整拓扑快照。
- 所有经营建议均为 advisory；只有经授权、类型化校验、人工确认和后置验证的后续
  专项工作才可能引入真实写动作，本路线不提供该授权。
