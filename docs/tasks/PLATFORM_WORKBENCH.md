## 模块信息与确认

**阶段**：`3 业务应用`（如系统另设「平台基础」阶段则归入该阶段）
**排程方式**：`并行`

### 模块背景

```
在三个业务模块（M4 智能客服、M5 运营辅助、M6 竞品分析）之外，本模块承担支撑
它们运行的平台基础能力：渠道适配层、知识与 SOP 的灰度发布、商品实体识别、
人工接管的排班与可见性、发布策略的夜间值守，以及若干阻断性缺陷修复。

这些工作是业务模块的前置依赖——没有渠道适配 SDK，客服模块无法接入任何真实
渠道；没有灰度发布，知识与 SOP 的版本切换会直接影响在途会话；没有商品实体
识别，客服回答商品咨询时只能让顾客报内部 SKU 编号。

本模块登记在项目功能台账的以下条目：F-101 渠道适配器 SDK、F-103 统一渠道会话
与可信上下文扩展、F-104 分层知识灰度发布、F-105 SOP 版本化执行与灰度、
F-106 ContextBuilder 与商品/SKU 顾问、F-107 四种人机协同接待模式、
F-109 人工客服工作台、F-119 坐席调度、F-120 值守排班。
```

### 总体需求

```
1. 渠道接入基础
   定义与具体平台解耦的适配器契约（能力声明、验签、标准消息信封、发送、回执、
   错误分类、去重、回放、限流），并用协议不同的第二个模拟渠道验证契约的通用性。
   消息信封需覆盖多种消息类型，非文本入站不拒收而是记录并强制转人工。

2. 知识与 SOP 的安全版本切换
   已批准的候选版本按会话稳定分桶灰度，支持调量、原子完成与一步回滚；
   在途会话固定启动版本，灰度回滚不影响已固定的运行；评测与进化路径永远只见
   基线，不观察半released 状态。

3. 商品实体识别
   顾客用名称、品类、型号、颜色描述商品时，系统需将描述解析为具体 SKU 并给出
   可解释的候选排序，而不是向顾客索要内部编号；对比类问题输出逐属性差异。

4. 人工接管的排班与可见性
   周期批量排班、订单关联的人工任务状态可见、发布策略的夜间值守时间窗与
   SOP 白名单、后台对渠道适配器与灰度状态的可视化。

5. 阻断性缺陷修复
   模型流式响应的错误处理、利润费用的数值截断。

约束：所有能力沿用项目既有的租户隔离、来源版本与载荷哈希、幂等写入、乐观锁、
审计底座，不新建平行机制；不改变既有 API 的响应契约。
```

### 验收标准

```
【功能验收】
1. 渠道适配契约由两个协议不同的适配器共同验证通过，渠道运行时与具体平台解耦
2. 非文本入站消息记录并以脱敏占位符落库，不进模型，强制转人工
3. 知识与 SOP 灰度：分桶稳定、调量生效、完成原子、回滚一步到位；
   已固定的运行在回滚后不换版本
4. 商品实体识别返回带版本号的稳定证据 ID；对比类问题输出逐属性差异表
5. 周期批量排班可按 UTC 绝对时间生成班次
6. 夜间值守时间窗跨零点正确；SOP 白名单未列入即违规并转人工
7. 后台可见渠道适配器、灰度状态与夜间值守策略

【工程验收】
8. 全量测试通过且用例数增长可归因
9. 每项能力具备反证：临时移除后对应测试必须失败
10. 跨租户、跨店铺数据不可合并，敌意载荷字段不可达 checkpoint
11. schema 变更为 additive，可从任意历史版本前向迁移
12. 既有 API 契约零变化

【边界声明】
真实渠道联调仍阻塞于平台资质与授权，本阶段以显式虚拟适配器完成本机验收，
不构成生产结论。
```
