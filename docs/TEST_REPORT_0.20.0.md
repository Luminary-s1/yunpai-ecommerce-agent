## 4. 实现中修正的问题

### 4.1 服务重启不应复活过期坐席

初版启动补种逻辑会刷新已有管理员的在线租约，导致已经离线的坐席在进程重启后重新变为可接单。修复后只为首次创建的 bootstrap 坐席建立租约；已有档案保留原租约，过期后始终按 `offline` 处理。

### 4.2 迁移标记不能掩盖物理结构缺失

schema v20 初版在检查迁移漂移前执行坐席补种，伪造迁移标记但缺少表的数据库会先触发普通 SQL 错误。修复后先检查 v20 物理表，再执行补种和完整结构校验，使损坏数据库以明确的 schema drift 错误拒绝启动。

### 4.3 旧测试中的任意负责人不再合法

0.19.0 测试可以直接用任意字符串认领任务；0.20.0 这会绕过真实资格模型。旧测试已统一建立有效管理员、坐席档案、在线租约和队列成员关系，确保回归测试验证的是新契约而非保留后门。

## 5. 数据库和迁移

- 新建库直接初始化 schema v20；
- v19 数据前向迁移后保留队列、任务、SLA、事件和版本；
- `handoff_operator_profiles` 保存档案、配置在线状态、租约、技能、容量和乐观锁版本；
- `handoff_operator_queue_memberships` 保存队列成员、L1-L5 熟练度和主队列；
- 触发器拒绝坐席档案与队列的跨租户组合；
- 活动管理员只补缺失档案和成员关系，不覆盖已经存在的运营配置；
- 伪造 schema v20 标记但缺表、缺列、缺索引或缺外键会拒绝启动；
- 运行库 `PRAGMA integrity_check=ok`，`foreign_key_check` 为空。

## 6. 调度算法与并发语义

领取或转派的资格条件为：

```text
admin credential active
and operator profile active
and effective presence == available
and member of target queue
and active tasks < global operator limit
and queue active tasks < queue per-operator limit
```

智能分配只接受未分配的 `proposed` 任务。候选人按以下稳定顺序选择：全局负载率低者优先、主队列优先、熟练度高者优先、活动任务少者优先，最后以 `operator_id` 字典序打破平局。

选择和写入发生在数据库写事务中。任务必须仍为 `proposed`、未分配且版本匹配；否则返回冲突，不用过期候选降级分配。成功后状态变为 `accepted`，写入负责人、`acknowledged_at`、新版本、`claimed` 事件和审计记录。

## 11. 发布建议

将 0.20.0 用作本地或客户隔离环境的坐席调度候选。下一阶段先由客服主管导入真实组织、队列、技能、班次和 SLA 配置，再用客户脱敏会话与固定模型建立评测基线，随后接真实渠道 shadow 和 assist。生产 `automatic` 继续关闭，所有生产 Gate 具备可复核证据并由业务、安全和运维签收后才能放行。
